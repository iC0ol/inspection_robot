# System Architecture

## 1. Overview

The inspection robot is currently implemented as a differential-drive mobile robot using ROS 2 Humble and Nav2.

The navigation stack is separated into several layers:

1. Simulation and robot control
2. State estimation
3. Localization
4. Environment representation
5. Planning
6. Local control
7. Behavior coordination
8. Mission orchestration (M6)

This separation allows individual components to be tested independently.

## 2. Coordinate Frames

The main TF structure is:

```text
map
 |
 v
odom
 |
 v
base_footprint
 |
 v
base_link
 |
 +---- laser_link
 |
 +---- other sensor frames
```

Frame ownership:

| Transform | Publisher |
|---|---|
| `map -> odom` | AMCL |
| `odom -> base_footprint` | EKF |
| robot fixed transforms | robot_state_publisher |

The differential-drive controller does not publish the main `odom -> base_footprint` transform.

This avoids multiple TF publishers competing for the same transform.

## 3. State Estimation

Raw wheel odometry is generated by the differential-drive controller.

The current simulated IMU provides angular velocity information.

These measurements are fused by `robot_localization`:

```text
Wheel Odometry ----+
                   |
                   v
                  EKF
                   |
IMU ---------------+
                   |
                   v
          /odometry/filtered
                   |
                   v
       odom -> base_footprint
```

A small yaw-rate deadband is applied to the simulated IMU to prevent numerical wheel-velocity noise from accumulating into stationary yaw drift.

## 4. Localization

AMCL performs localization against the saved occupancy grid.

Inputs:

```text
/map
/scan
odom -> base_footprint
```

Output:

```text
map -> odom
```

Therefore the complete global pose becomes available through:

```text
map
 |
 v
odom
 |
 v
base_footprint
```

For the current Gazebo inspection-room simulation, the known map-frame initial pose is supplied automatically by the simulation launch configuration.

Real robot operation should not assume this fixed initial pose.

## 5. Costmaps

### Global Costmap

Purpose:

- represent the global navigation environment
- combine saved map information and currently observed obstacles
- provide the cost representation used by the global planner

Configuration:

```text
Frame: map
Rolling window: false
Resolution: 0.05 m
```

Layers:

```text
Static Layer
     +
Obstacle Layer
     +
Inflation Layer
```

### Local Costmap

Purpose:

- represent the environment immediately surrounding the robot
- support local collision avoidance
- continuously move with the robot

Configuration:

```text
Frame: odom
Rolling window: true
Size: 3 m × 3 m
Resolution: 0.05 m
```

Layers:

```text
Obstacle Layer
     +
Inflation Layer
```

## 6. Global Planning

The current global planner is NavFn:

```text
nav2_navfn_planner/NavfnPlanner
```

The planner receives:

```text
Current Pose
Goal Pose
Global Costmap
```

and generates:

```text
nav_msgs/Path
```

The current configuration uses Dijkstra-style NavFn planning rather than A*.

## 7. Local Controller

The project currently uses the Dynamic Window Based controller:

```text
dwb_core::DWBLocalPlanner
```

DWB samples possible velocity commands and predicts their short-term trajectories.

Candidate trajectories are evaluated according to critics such as:

- obstacle cost
- path alignment
- distance to path
- goal alignment
- distance to goal
- rotate-to-goal behavior

The selected command is published to:

```text
/diff_drive_controller/cmd_vel_unstamped
```

which is executed by the differential-drive controller.

## 8. Behavior Tree Navigation

High-level navigation is coordinated by `bt_navigator`.

The main conceptual pipeline is:

```text
NavigateToPose
      |
      v
ComputePathToPose
      |
      v
FollowPath
```

The behavior tree also provides recovery operations including:

```text
Clear Costmap
Spin
Wait
BackUp
```

The default navigation tree periodically recomputes the global path while the controller continuously follows the latest path.

This allows the robot to respond to changes in the environment.

## 9. Dynamic Obstacle Handling

The dynamic obstacle pipeline is:

```text
Gazebo obstacle
      |
      v
LaserScan
      |
      v
Obstacle Layer
      |
      v
Global / Local Costmap
      |
      +----------------+
      |                |
      v                v
Global Replan      DWB avoidance
      |                |
      +-------+--------+
              |
              v
          Robot Motion
```

During validation, obstacles introduced after map creation were detected by the laser scanner and inserted into the costmaps.

When a global route became blocked, the planner generated an alternative route.

When the obstacle was removed, subsequent replanning could again use the shorter route.

## 10. Lifecycle Management

Nav2 lifecycle nodes are automatically managed by two lifecycle managers.

Localization:

```text
map_server
amcl
```

Navigation:

```text
planner_server
controller_server
behavior_server
bt_navigator
```

The integrated simulation startup therefore does not require manually running:

```text
ros2 lifecycle set ...
```

## 11. Launch Architecture

### gazebo.launch.py

Responsible for:

```text
Gazebo
Robot Spawn
robot_state_publisher
ros2_control
mock IMU
EKF
```

### navigation.launch.py

Responsible for:

```text
Map Server
AMCL
Global Planner
Local Controller
Behavior Server
BT Navigator
Lifecycle Managers
```

It is intentionally kept separate from Gazebo so that the navigation stack can later be reused for the physical robot.

### simulation_navigation.launch.py

Simulation integration layer:

```text
gazebo.launch.py
        +
navigation.launch.py
        +
simulation initial pose
        +
RViz
```

This is the normal entry point for the current simulation system.

## 12. Diagnostic Tools

The normal navigation interface is:

```text
NavigateToPose
```

For component-level debugging, `plan_and_follow.py` can bypass BT Navigator:

```text
ComputePathToPose
        |
        v
   FollowPath
```

This is useful when determining whether a navigation problem originates in:

```text
Planner
Controller
or
Behavior Tree orchestration
```

## 14. M6 Mission Management Layer

M6 adds a mission orchestration layer **above** Nav2 without replacing the M5
navigation stack. Localization, costmaps, path planning, recovery behaviors, and
velocity control remain the responsibility of the existing Nav2 system.

```text
                  Operator / UI
                 /            \
      /mission/status       /mission/cancel
               \              /
                v            v
             Mission Manager
          (sequence, retry, skip,
           wait, cancel, status)
                      |
                      | NavigateToPose Action
                      v
              Nav2 BT Navigator
                      |
             M5 navigation stack
                      |
                      v
                Robot motion
```

### 14.1 Responsibility Boundaries

- `mission_model.py` maintains mission and waypoint states, retry budgets,
  and failure policies without requiring ROS communication.
- `mission_manager.py` translates model decisions into asynchronous Nav2
  Action goals, ROS timers, cancellation handling, and status services.
- `mock_nav2_server.py` supplies configurable fake `NavigateToPose` results
  for automated integration tests without Gazebo.

The Mission Manager executes a **one-shot** mission; it is not yet a
persistent fleet, scheduling, or inspection-data collection service.

### 14.2 Mission State Transitions

Normal waypoint progression:

```text
PENDING -> NAVIGATING -> INSPECTING -> SUCCEEDED
                 |
                 +-- ABORTED -> RETRY_PENDING -> NAVIGATING
                 |
                 +-- retry exhausted -> FAILED or SKIPPED
```

The mission finishes as `SUCCEEDED`, `FAILED`, `CANCELED`, or
`COMPLETED_WITH_SKIPS` according to the configured outcome. `PAUSED` is
reserved in the model, but pause/resume is not implemented.

`max_navigation_retries` specifies additional attempts after the initial
navigation attempt. Exhaustion can fail the full mission (`FAIL_MISSION`)
or skip a waypoint (`SKIP_WAYPOINT`).

### 14.3 Communication Interfaces

| Interface | Type | Purpose |
| --- | --- | --- |
| `/navigate_to_pose` | `nav2_msgs/action/NavigateToPose` | Dispatch navigation goals |
| `/mission/cancel` | `std_srvs/srv/Trigger` | Request mission cancellation |
| `/mission/status` | `std_srvs/srv/Trigger` | Query running mission state |

Cancellation is asynchronous. While an Action goal remains unresolved,
the status service can report `mission=RUNNING` together with
`phase=CANCEL_REQUESTED`. When the mission terminates, the current
Mission Manager process exits, so status history is not retained.

**Safety boundary:** A returned service response or an internal mission
terminal state does not prove that the physical robot has stopped.
Uncertain Nav2 Action results require additional motion-state verification
and independent safety measures on real hardware.

### 14.4 Automated Verification

The M6 test suite includes model unit tests, callback exception-injection
tests, and `launch_testing` integration tests for retry, retry exhaustion,
skip, accepted cancellation, and rejected cancellation.

ROS Domain isolation during the pytest session is provided through
`domain_coordinator` and `test/conftest.py`. Run the package tests with:

```bash
colcon test --packages-select inspection_robot_mission
colcon test-result --verbose
```

See [`mission_manager.md`](mission_manager.md) for the detailed architecture,
configuration parameters, test scenarios, and execution instructions.
