System Architecture
1. Overview
The inspection robot is currently implemented as a differential-drive mobile robot using ROS 2 Humble and Nav2.
The navigation stack is separated into several layers:
Simulation and robot control
State estimation
Localization
Environment representation
Planning
Local control
Behavior coordination
This separation allows individual components to be tested independently.
2. Coordinate Frames
The main TF structure is:
```text
map
 |
 v
odom
 |
 v
base_footprint
 |
 v
base_link
 |
 +---- laser_link
 |
 +---- other sensor frames
```
Frame ownership:
Transform	Publisher
`map -> odom`	AMCL
`odom -> base_footprint`	EKF
robot fixed transforms	robot_state_publisher
The differential-drive controller does not publish the main `odom -> base_footprint` transform.
This avoids multiple TF publishers competing for the same transform.
3. State Estimation
Raw wheel odometry is generated by the differential-drive controller.
The current simulated IMU provides angular velocity information.
These measurements are fused by `robot_localization`:
```text
Wheel Odometry ----+
                   |
                   v
                  EKF
                   |
IMU ---------------+
                   |
                   v
          /odometry/filtered
                   |
                   v
       odom -> base_footprint
```
A small yaw-rate deadband is applied to the simulated IMU to prevent numerical wheel-velocity noise from accumulating into stationary yaw drift.
4. Localization
AMCL performs localization against the saved occupancy grid.
Inputs:
```text
/map
/scan
odom -> base_footprint
```
Output:
```text
map -> odom
```
Therefore the complete global pose becomes available through:
```text
map
 |
 v
odom
 |
 v
base_footprint
```
For the current Gazebo inspection-room simulation, the known map-frame initial pose is supplied automatically by the simulation launch configuration.
Real robot operation should not assume this fixed initial pose.
5. Costmaps
Global Costmap
Purpose:
represent the global navigation environment
combine saved map information and currently observed obstacles
provide the cost representation used by the global planner
Configuration:
```text
Frame: map
Rolling window: false
Resolution: 0.05 m
```
Layers:
```text
Static Layer
     +
Obstacle Layer
     +
Inflation Layer
```
Local Costmap
Purpose:
represent the environment immediately surrounding the robot
support local collision avoidance
continuously move with the robot
Configuration:
```text
Frame: odom
Rolling window: true
Size: 3 m × 3 m
Resolution: 0.05 m
```
Layers:
```text
Obstacle Layer
     +
Inflation Layer
```
6. Global Planning
The current global planner is NavFn:
```text
nav2_navfn_planner/NavfnPlanner
```
The planner receives:
```text
Current Pose
Goal Pose
Global Costmap
```
and generates:
```text
nav_msgs/Path
```
The current configuration uses Dijkstra-style NavFn planning rather than A*.
7. Local Controller
The project currently uses the Dynamic Window Based controller:
```text
dwb_core::DWBLocalPlanner
```
DWB samples possible velocity commands and predicts their short-term trajectories.
Candidate trajectories are evaluated according to critics such as:
obstacle cost
path alignment
distance to path
goal alignment
distance to goal
rotate-to-goal behavior
The selected command is published to:
```text
/diff_drive_controller/cmd_vel_unstamped
```
which is executed by the differential-drive controller.
8. Behavior Tree Navigation
High-level navigation is coordinated by `bt_navigator`.
The main conceptual pipeline is:
```text
NavigateToPose
      |
      v
ComputePathToPose
      |
      v
FollowPath
```
The behavior tree also provides recovery operations including:
```text
Clear Costmap
Spin
Wait
BackUp
```
The default navigation tree periodically recomputes the global path while the controller continuously follows the latest path.
This allows the robot to respond to changes in the environment.
9. Dynamic Obstacle Handling
The dynamic obstacle pipeline is:
```text
Gazebo obstacle
      |
      v
LaserScan
      |
      v
Obstacle Layer
      |
      v
Global / Local Costmap
      |
      +----------------+
      |                |
      v                v
Global Replan      DWB avoidance
      |                |
      +-------+--------+
              |
              v
          Robot Motion
```
During validation, obstacles introduced after map creation were detected by the laser scanner and inserted into the costmaps.
When a global route became blocked, the planner generated an alternative route.
When the obstacle was removed, subsequent replanning could again use the shorter route.
10. Lifecycle Management
Nav2 lifecycle nodes are automatically managed by two lifecycle managers.
Localization:
```text
map_server
amcl
```
Navigation:
```text
planner_server
controller_server
behavior_server
bt_navigator
```
The integrated simulation startup therefore does not require manually running:
```text
ros2 lifecycle set ...
```
11. Launch Architecture
gazebo.launch.py
Responsible for:
```text
Gazebo
Robot Spawn
robot_state_publisher
ros2_control
mock IMU
EKF
```
navigation.launch.py
Responsible for:
```text
Map Server
AMCL
Global Planner
Local Controller
Behavior Server
BT Navigator
Lifecycle Managers
```
It is intentionally kept separate from Gazebo so that the navigation stack can later be reused for the physical robot.
simulation_navigation.launch.py
Simulation integration layer:
```text
gazebo.launch.py
        +
navigation.launch.py
        +
simulation initial pose
        +
RViz
```
This is the normal entry point for the current simulation system.
12. Diagnostic Tools
The normal navigation interface is:
```text
NavigateToPose
```
For component-level debugging, `plan_and_follow.py` can bypass BT Navigator:
```text
ComputePathToPose
        |
        v
   FollowPath
```
This is useful when determining whether a navigation problem originates in:
```text
Planner
Controller
or
Behavior Tree orchestration
```

The complete validated pipeline is:
```text
                 Gazebo
                    |
              Robot + Laser
                    |
          +---------+---------+
          |                   |
          v                   v
     Wheel Odom             /scan
          |                   |
          v                   |
         EKF                  |
          |                   |
          v                   |
odom -> base_footprint        |
          |                   |
          +---------+---------+
                    |
                    v
                   AMCL <------ /map
                    |
                    v
               map -> odom
                    |
                    v
              Global Costmap
                    |
                    v
               NavFn Planner
                    |
                    v
               Global Path
                    |
                    v
                DWB Controller
                    |
                    v
                  cmd_vel
                    |
                    v
          diff_drive_controller
                    |
                    v
                  Robot
```
BT Navigator coordinates the planner, controller, and recovery behaviors above this pipeline.
